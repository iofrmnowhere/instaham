Short version: none of the Python ships. The industry practice is to treat those helper files as a **reference implementation** that lives in your training repo, and to move each piece of logic into one of three places on device, in this order of preference.

## 1. Push as much as possible into the model graph

This is the biggest win and the one most teams under-use. Anything that's plain tensor math should become part of the exported artifact rather than code you have to rewrite.

For ONNX, wrap your model in a thin `nn.Module` whose `forward` does the preprocessing, calls the network, and does the postprocessing, then export that. Resize, mean/std normalization, channel transpose, sigmoid/softmax, `argmax` over the class axis, threshold comparisons, and even upsampling the mask back to input resolution all trace cleanly. For TFLite/LiteRT, do the same with a `tf.function` and a fixed input signature, or with Keras preprocessing layers before conversion.

The goal is that your Dart code hands over a `Uint8List` of pixels and gets back a `Uint8List` label mask, with nothing in between. Every op you fold in is code you don't have to port twice and keep in sync.

## 2. Port the leftovers to Dart

Whatever won't trace goes to Dart: control flow, connected-component filtering, "keep the largest blob", polygon extraction, mask-to-overlay conversion. Write it against typed data (`Float32List`, `Uint8List`) with flat indexing and no per-pixel closures, and run it in an isolate so you don't jank the UI thread.

## 3. Drop to C++ via FFI only when Dart is too slow

If you're doing real per-pixel work at camera frame rate (morphological open/close, distance transforms, contour tracing, CRF refinement), the standard move is a small C++ shim over OpenCV compiled for both platforms and called through `dart:ffi` with bindings generated by `ffigen`. It's more build complexity, so only pay for it after you've measured. For segmentation specifically, postprocessing is often a real fraction of end-to-end latency, not a rounding error, so it's worth profiling the three stages separately.

## What to avoid

Embedding a Python interpreter (Chaquopy, BeeWare, etc.) is not a practice anyone follows for Flutter. Android-only, tens of megabytes, and it drags NumPy/OpenCV/Pillow along with it.

## The part people skip: parity tests

This is what actually makes the migration safe. Keep the Python helpers in the repo as the source of truth and build a golden-file harness:

- Run the Python pipeline over 20–50 representative images.
- Dump every intermediate as raw binary or `.npy`: the preprocessed input tensor, the raw model output, the final mask.
- Ship those fixtures into your Flutter test assets.
- Write Dart tests asserting your ported implementation matches within tolerance (exact match for the label mask, small epsilon for float tensors), plus an IoU check against the Python mask.

Now when someone changes a helper in Python, the Dart test fails, and you find out at CI time rather than from a user with a subtly wrong mask.

## Mismatches that will bite you

Almost every "works in Python, wrong on device" bug in this pipeline comes from the same short list:

- **Resize interpolation.** PIL bilinear, OpenCV bilinear, and Dart's `image` package `copyResize` do not agree, especially when downscaling, because of antialiasing and pixel-center conventions. Pick one and replicate it, or fold the resize into the graph so it's the runtime's problem.
- **Letterbox vs stretch**, and whether you remember to un-letterbox the mask afterward.
- **Channel order and normalization order.** RGB vs BGR, and whether you divide by 255 before or after subtracting the mean.
- **NHWC vs NCHW.** TFLite wants NHWC, PyTorch exports NCHW. Ultralytics has documented measurable latency differences between the two layouts for semantic segmentation exports.
- **Quantization scale and zero point** if you go INT8. Dequantize with the values baked in the model, never hardcoded.

For the runtime itself, `flutter_onnxruntime` and `onnxruntime_v2` are the maintained ONNX options on pub.dev (the original `onnxruntime` package has gone quiet), and `tflite_flutter` remains the common LiteRT choice.
