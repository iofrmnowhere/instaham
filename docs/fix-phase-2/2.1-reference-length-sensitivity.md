# Phase 2.1 — One pixel of reference marking moves the estimate by 5%

Status: measured — all three photos swept on device with the shipped cutter in the loop
(18 scans, raw data in `docs/logs/recorded.md`). The jitter band is **5.2% / 12.0% / 12.6%**
of predicted weight on the 92, 96 and 118 kg photos. The dominant term is **item 3, the
cutter**, on two of the three photos, and a **fourth term not in the original three-item
model** — boundary-feature instability feeding a step-function regressor — dominates the
third.
Phase 2's method decision is settled and recorded below and in phase 2's own file.
**No fix has been applied; the amplifiers are still in the pipeline.**

Opened as a subphase of phase 2 rather than a phase of its own because it is not a separate
question from phase 2, it is a precondition for phase 2's method: phase 2 compares two
`cm_per_px_target` constants that differ by 6.4%, and this subphase shows the measurement it
would use carries noise of the same magnitude. Numbering continues at **F53**.

## Symptom

Re-marking the same reference object on the same photograph, moving one endpoint by a single
pixel at a time, changes the predicted weight far more than the input change can account for,
and not in one direction.

The user recorded six consecutive reference lengths on
`.pig_pictures/92kg_pig_meter_stick.HEIC` (true weight 92 kg, meter stick reference, so
`reference_cm` = 100). Raw data in `docs/logs/recorded.md`; the `cm_per_px` column is the
value the UI displayed, rounded to four decimals.

| reference px | `cm_per_px` shown | predicted kg |
|---|---|---|
| 1547 | 0.0646 | 84.4 |
| 1548 | 0.0646 | 83.5 |
| 1549 | 0.0646 | 88 |
| 1550 | 0.0645 | 88 |
| 1551 | 0.0645 | 87.3 |
| 1552 | 0.0645 | 87.3 |

Across those six rows the reference length varies by 0.32% and the prediction varies by
4.5 kg — 5.2% of the mean, roughly a **16× amplification**. The response is also
non-monotone: 1547 → 1548 falls, 1548 → 1549 rises by 4.5 kg, then it falls again. It is
repeatable, not random: the user confirmed that re-marking the *same* pixel length returns the
same weight.

The user's own report noted the displayed `cm_per_px` is rounded for display, so the six rows
are not necessarily six distinct underlying floats in the way the table suggests. That does
not change the finding — the endpoints of the range are unambiguously far apart in output and
close together in input.

## Root cause

### F53 — the reference length enters the pipeline in three places, and every one of them is a step function

The intuition behind the reference object is that it sets one linear constant. It does not.
`cm_per_px` is consumed three separate times, and none of the three responds smoothly.

**A fourth term was added after the on-device sweep** — see the second Measurement section
below. The regressor does not merely amplify jitter that items 1–3 hand it; on the 118 kg
photo it moved 5.84 kg while the mask area it was given changed by 0.04%, responding to
boundary features that items 2 and 3 destabilise without changing area. Items 1–3 as written
below are still correct; they are not the complete list.

**1. It changes the segmentation input, so the mask itself can change.** This is the term that
is easiest to miss and probably the largest. `pipeline.cpp:355-360` passes the user's measured
`cm_per_px` into `run_segmentation` as `cm_per_px_actual`, alongside the manifest's
`segmentation.input_scale.cm_per_px` (1.10). The segmenter places the photograph inside the
640×640 canvas at a content scale derived from their ratio — the `content_scale` and
`input_cm_per_px_used` fields published at `pipeline.cpp:367` and `pipeline.cpp:431-432`.

So moving the reference endpoint resizes the image that YOLO sees. A different input image can
produce a different detection, a different mask contour, or a different rung of the retry
ladder. This is not a rounding artifact downstream of a fixed mask — it is a different
segmentation. Nothing in the round 4 work that introduced the ladder (F18/F19) considered it
as a *sensitivity* question, only as a coverage one.

**2. The mask resample size is integer-quantized.** `construction.cpp:133-138`:

```cpp
const int scaled_w = std::max(1, int(std::lround(mask.width * k)));
const int scaled_h = std::max(1, int(std::lround(mask.height * k)));
cv::resize(src, resized, cv::Size(scaled_w, scaled_h), 0, 0, cv::INTER_NEAREST);
```

`k = cm_per_px / cm_per_px_target`. The photograph reaches the pipeline at **2250 × 3000**, not
at its native 3024 × 4032: `lib/core/utils/image_service.dart:61-62` and `:78-79` pass
`maxWidth: 3000, maxHeight: 3000` to both the camera and gallery pickers, so the long edge is
capped before anything else runs. (`ImageService.processRawBytes` itself does not resize — it
bakes EXIF orientation and re-encodes at quality 92 — so the cap is the picker's, and a capture
path that bypasses the picker would not have it.)

At 2250 × 3000 with `cm_per_px_target` 0.35, `scaled_w = lround(642857.14 / px)` and
`scaled_h = lround(857142.86 / px)`. Over the recorded range:

| reference px | resampled mask | recorded kg |
|---|---|---|
| 1547 | 416 × 554 | 84.4 |
| 1548 | 415 × 554 | 83.5 |
| 1549 | 415 × 553 | 88 |
| 1550 | 415 × 553 | 88 |
| 1551 | 414 × 553 | 87.3 |
| 1552 | 414 × 552 | 87.3 |

**1549 and 1550 resolve to the same grid cell and returned the same 88 kg.** That is a direct
corroboration of the quantization mechanic rather than a loose fit. The 87.3 pair spans two
adjacent cells, which a piecewise-constant regressor can also produce, so it neither confirms
nor contradicts. The displayed `cm_per_px` is rounded for display, so this table is computed
from the displayed integer pixel lengths; the underlying floats may sit slightly differently
within the cells, which is why the 1549/1550 agreement is treated as corroboration and not as
proof.

Beyond the size quantization, `INTER_NEAREST` at a ~5.4× downsample resamples *different
source pixels* whenever the output size changes. Area survives that; boundary statistics do
not. Eight of the sixteen `chen16_noheight` features are boundary-derived — `perimeter`,
`outline_curve`, `body_curve` and `Hu_1` through `Hu_7` — which phase 3's F48 already
identifies from the specification-divergence angle. F53 is the measured consequence of the
same mechanic.

**Three capture paths, three input resolutions — and the field path is the worst one.**
`capture_screen.dart:279-284` sends a live capture straight to `ImageService.processCapture`,
which reaches `processRawBytes` — and `processRawBytes` applies no cap of its own. The 3000 px
limit exists only on the two picker fallbacks. The controller is built at
`ResolutionPreset.high` (`capture_screen.dart:96`), which is 1280 × 720 on Android.

| path | reaches the pipeline at |
|---|---|
| live in-app camera, `takePicture()` | ~1280 × 720 (no cap applied) |
| gallery import, `pickFromGallery` | 2250 × 3000 for the `.pig_pictures/` photos |
| camera fallback (web/desktop), `pickFromCamera` | capped at 3000 on the long edge |

The *resampled* mask is roughly 415 × 553 on all three, because `k` scales inversely with input
resolution and the normalization is to a fixed physical scale — that part cancels. What does
not cancel is the precision of the user's marking. A meter stick spanning 1547 px in a
2250-wide import spans roughly 495 px at 720p, so one pixel of endpoint movement is 0.065% of
the reference on the path the recorded data came from and about 0.20% on the live-camera path
— roughly **three times more sensitive in normal field use than in the recorded test**.

The recorded 4.5 kg swing is therefore the optimistic case, and F53's measurement steps must
sweep both resolutions rather than only the gallery import. (`ResolutionPreset.high` mapping to
720p is the camera plugin's documented Android behaviour, not something measured on the user's
device; the still-capture resolution should be confirmed from a real capture's
`widthPx`/`heightPx` before the numbers above are quoted as final.)

**3. The cutter runs after the resample, on that shifting grid.** `pipeline.cpp:667-697`
resamples first and points `mask_for_cutter` at the scaled mask, so `cut_body_mask` sees a
different pixel grid at every step. The V176/V144 cutter is threshold-heavy — skeletonization,
peak finding, circle fitting, candidate selection — and its decisions are discrete. A
one-pixel change in its input can select a different lobe and move the cut by percent-level
area, not sub-pixel amounts.

**And the regressor on top of all three is piecewise-constant.** XGBoost is a sum of decision
trees; its output is a step function of its inputs and is not monotone in mask area. Plateaus
and jumps are its native behaviour, not evidence of a bug on their own. What F53 asserts is
that stages 1–3 feed it input jitter large enough to cross splits.

### Why this is not simply phase 3 restated

Phase 3 (F48/F49) asks whether the *specified* order — resize the whole photograph before
segmentation — should replace the implemented order. It is a conformance question with no
user-visible defect attributed to it. F53 is a measured behaviour with a recorded reproduction,
and its item 1 concerns the segmenter's own input-scale contract, which phase 3 explicitly
treats as fixed and working (its section "For the current order" cites
`segmentation.input_scale.cm_per_px: 1.1` and the F18/F19 ladder as confirmed on device).

The two do meet at item 2. If phase 3 adopts the specification's order — resize the whole
photograph by `scale_factor` before segmenting, rather than resampling the mask afterwards —
then item 2 disappears outright, because there is no separate mask resample left to quantize.

**Item 1 survives that change, and this is the part worth being clear about.** Under the
specification's order the reference length still decides how large the image is when the
segmenter sees it, so a one-pixel marking change still produces a different segmenter input
and can still produce a different mask. Phase 3 removes one of the three amplifiers, not all
of them. That is a reason to record F53's findings where phase 3 can consume them, not a
reason to defer F53 until phase 3 is decided — and it means phase 3 must not be sold as the
fix for F53 without measuring what item 1 contributes on its own.

Note also that the 3000 px picker cap is a *different* shrink from either: it is a fixed
memory/performance limit applied before any of this, not derived from the reference object and
not part of scale normalization. It does not belong to phase 3's question.

### Why phase 2 cannot be measured first

Phase 2's method is to run the three `.pig_pictures/` photos at `cm_per_px_target` 0.35 and at
0.3289 and compare the errors. The two constants differ by 6.4%. The 92 kg photo alone spans
83.5–88 kg on reference marking that a user could not distinguish by eye. Running phase 2's
comparison without first bounding this would produce a number whose sign depends on where the
marker happened to land, and it would look like a result.

The already-recorded 87.36 kg for this photo (phase 1.1's verification, from
`scan_hm2nkeb6se_iaainz`) sits inside the observed 83.5–88 band. It is one sample from a
distribution, not a point measurement, and phase 2 should treat it as such.

## Measurement — host-side attribution sweep (92 kg photo only)

A host-side script (not committed) reproduced the real segmentation ONNX, the real chen16
feature extractor, and the real xgboost ONNX, sweeping reference pixel length px 1520–1580 (a
±2% band around the recorded 1547–1552 cluster) on `92kg_pig_meter_stick.HEIC`. It explicitly
**excludes the shipped C++ V176/V144 cutter** — no host build target exists for `pipeline.cpp`
(`docs/handoff.md`), and `ML/pipeline/cutter.py` is a different algorithm, the Python training
reference, not the shipped port — so every number below is a **lower bound**: item 3 sits on
top of this and was not measured.

**Both item 1 and item 2 are real and large, not one dominant and one negligible as originally
guessed:**

| what was isolated | how | spread |
|---|---|---|
| item 1 alone — segmenter mask vs. reference length | mask area across the sweep | **6.10%** (13 distinct areas over 61 px values) |
| item 2 alone — resample quantization vs. reference length | fixed mask (from px 1550), only `k` varies | **11.08 kg / 12.41%** |
| item 1 + item 2 combined, gallery-import resolution (2250×3000) | re-segment and re-resample per px | **10.25 kg / 11.45%**, true weight 92 |
| item 1 + item 2 combined, simulated live-camera resolution (~540×720) | same, image fit to 1280×720 before segmenting — **not a real device capture** | **9.50 kg / 10.31%** |
| recorded on-device, gallery-import path (`docs/logs/recorded.md`) | 6 hand-marked points, narrower band (±3 px vs. this sweep's ±30 px) | 4.5 kg / 5.2% |

The recorded on-device figure is smaller than the host sweep's combined figure mainly because
it covers a narrower band (±3 px, not ±30 px) and because it excludes whatever the real cutter
does to the result — it is not evidence that the true sensitivity is only 5.2%.

**A secondary finding:** segmenter confidence itself varies 0.883–0.916 across the sweep with
no trend against pixel length. The detector is not merely being resampled differently each
step, it is genuinely uncertain at this input scale — worth keeping in mind if item 1's fix is
ever discussed, since a confidence-threshold change interacts with it.

**Caveats on this measurement, restated:** no real cutter (lower bound, see above); the
"simulated live-camera resolution" row scales the whole frame to fit 1280×720 rather than
reproducing a real device capture's crop/aspect, so it is indicative, not exact; only the
92 kg photo was run — the other two `.pig_pictures/` photos are still open (step below).

## Measurement — on-device sweep, all three photos, shipped cutter included

This is the measurement the host sweep above could not make. It runs the real APK, so the
shipped C++ V176/V144 cutter is in the loop and item 3 is no longer excluded.

**Method.** Six marks per photo, stepped about 3 px apart across a roughly 16 px band centred
on a natural mark — 0.7–1.0% of each photo's reference length. Each mark is a full
`adb logcat -c` / mark / confirm / `adb logcat -d >>` cycle, one dump file per photo, so no
scan is lost to logcat ring-buffer overflow (an earlier attempt at batching all marks before
one dump lost every scan but the last). 18 scans total, all at `cm_per_px_target` 0.35, all
at `ladder_rung` 0, all `cutter.status: cut_applied`. Full per-scan table in
`docs/logs/recorded.md`.

`ref_px` throughout is back-computed as `reference_cm / scale.cm_per_px_actual` from the
envelope rather than read from the UI, so it is the length the pipeline actually used and the
display-rounding caveat that qualified the first six hand-recorded rows does not apply here.

### The bands

| photo | true kg | predicted range | spread | monotone? |
|---|---|---|---|---|
| 92 kg meter stick | 92 | 83.54 – 88.03 | 4.49 kg / **5.18%** | no |
| 96 kg porac stick | 96 | 78.53 – 88.84 | 10.31 kg / **12.04%** | no |
| 118 kg porac stick | 118 | 104.80 – 118.49 | 13.69 kg / **12.55%** | yes, decreasing |

The 92 kg figure reproduces the 5.2% already recorded by hand, on an independent set of marks
— the original six rows are not a fluke of that sitting.

### Attribution, per term

The envelope separates the terms cleanly because it publishes both
`construction.mask_area_px` (the mask in original image coordinates, **before** the resample,
so it moves only when segmentation itself changed — item 1) and `features.values.mask_area`
(**after** resample and after the cut, which is what the regressor is given — items 1+2+3).

| photo | item 1 (`segArea`) | item 3 (`kept_fraction`) | items 1+2+3 (`featArea`) | predicted kg |
|---|---|---|---|---|
| 92 kg | 3.38% | 8.55% | 10.36% | 5.18% |
| 96 kg | 0.98% | 16.08% | 15.77% | 12.04% |
| 118 kg | 0.39% | 0.74% | 2.61% | 12.55% |

**Item 1 is the smallest term, not the largest.** The host sweep guessed item 1 was "probably
the largest" and measured 6.10% of mask area across a ±30 px band; across these narrower,
realistic ±8 px bands the segmentation mask moves 0.39–3.38%. Segmentation does change — the
92 kg photo produced three distinct `segArea` values and the 96 kg photo two — but it is not
what drives the weight.

**The smooth expectation is roughly 2× the pixel span.** `k` is proportional to `1/ref_px` and
the resampled area to `k²`, so a 1% band should move the regressor's mask area about 2%. Every
photo exceeds that: 10.36% against 2.02% (5.1×), 15.77% against 1.48% (10.7×), 2.61% against
1.58% (1.7×).

### Item 3 isolated: the cutter takes a different cut from an identical mask

Two pairs of adjacent marks share an **identical** `construction.mask_area_px`, so
segmentation returned the same mask and item 1 is exactly zero across them. Everything that
follows is the resample grid shifting under the cutter:

| photo | marks | segArea | kept_fraction | featArea | predicted kg |
|---|---|---|---|---|---|
| 96 kg | 2072.14 → 2074.68 px | 1501254 (identical) | 0.8063 → 0.9507 | +17.66% | 78.53 → **88.84** (+10.31) |
| 92 kg | 1547.62 → 1550.52 px | 1356422 (identical) | 0.8705 → 0.9356 | +7.30% | 83.54 → **88.03** (+4.49) |

A 2.5 px change in where the user marked a stick, with the segmentation mask bit-identical,
moved the cut by 14.4 percentage points of retained area and the answer by 10.31 kg. This is
item 3 measured on its own, and on these two photos it is the whole finding. The host sweep's
disclaimer that its figures were a lower bound is confirmed: the term it could not run is the
term that matters most here.

Both jumps are the cutter **retaining more**, i.e. the low `kept_fraction` marks are the
outliers. The V176 selection is choosing a different lobe or a different break, not shaving
the same cut slightly differently.

### The fourth term: the regressor steps on boundary features while area sits still

The 118 kg photo does not fit the item-1/2/3 model at all. Its inputs are the most stable of
the three — `segArea` spread 0.39%, `kept_fraction` spread 0.74%, `featArea` spread 2.61% —
and its predicted weight has the **largest** spread of the three at 12.55%.

The decisive pair is 2009.47 → 2012.31 px, again with an identical `segArea` of 1813602:

| quantity | 2009.47 px | 2012.31 px | change |
|---|---|---|---|
| `features.mask_area` | 58565 | 58543 | **−0.04%** |
| `convex_hull_area` | 61592 | 61531 | −0.10% |
| `kept_fraction` | 0.9285 | 0.9330 | +0.48% |
| `perimeter` | 1048.52 | 1051.94 | +0.33% |
| `longest` | 409.52 | 411.57 | +0.50% |
| `shortest` | 151.0 | 150.0 | −0.66% |
| `body_curve` | 173.30 | 174.92 | +0.94% |
| `outline_curve` | 0.031270 | 0.036342 | **+16.22%** |
| `Hu_5` | 8.7185e-10 | 1.0686e-09 | **+22.56%** |
| `Hu_6` | 1.0225e-07 | 2.3399e-07 | **+128.84%** |
| **estimated_kg** | **112.88** | **107.04** | **−5.84 kg (−5.2%)** |

Mask area is unchanged to four significant figures and the answer moves 5.84 kg. The features
that moved are the boundary-derived ones, and `outline_curve` and the Hu moments moved by
tens to hundreds of percent while area held still.

This is the mechanism the write-up above predicted but had not measured: `INTER_NEAREST` at a
~5.4× downsample preserves area and destroys boundary statistics, and eight of the sixteen
`chen16_noheight` features are boundary-derived. The consequence is now measured — and it is
not a small correction on top of the area terms, it is independently capable of a 5% weight
swing with the area term contributing nothing.

The Hu moments are the worst of them. Across adjacent marks anywhere in the 18 scans, `Hu_3`
through `Hu_7` swing by hundreds to thousands of percent (one 96 kg pair moves `Hu_5` by
−4037%, another by +4992%). They are near-zero quantities so a large relative change is not by
itself alarming, but they are 5 of the 16 inputs the regressor splits on, and nothing in the
pipeline stabilises them.

`shortest` is separately worth noting: it comes back integer-valued (112.0, 149.0, 150.0,
151.0), so it is quantized and steps by ~0.7% at a time regardless of how finely the user
marks.

### What this says about phase 2

Every photo reads **low** at `cm_per_px_target` 0.35, across essentially its whole band:

| photo | true | band | median | median error |
|---|---|---|---|---|
| 92 kg | 92 | 83.54 – 88.03 | 87.07 | −5.4% |
| 96 kg | 96 | 78.53 – 88.84 | 86.66 | −9.7% |
| 118 kg | 118 | 104.80 – 118.49 | 106.72 | −9.6% |

Phase 2's first step predicted exactly this test: "if the three field photos read low after
phase 1 restores the branch, that supports the specification's value". They read low on all
three, by 5–10% at the median. That is a real signal in 0.3289's favour and it is new — F38's
two-photo `RA` table pointed the other way.

It is **not** a result yet, for two reasons. First, the bands overlap the signal: 0.35 and
0.3289 differ by 6.4%, roughly 13% in predicted weight, and two of the three photos carry a
12%+ jitter band of their own. Second, the predictions cannot be extrapolated to 0.3289 by
multiplying by 13% — this subphase has just finished demonstrating that the regressor is a
step function that moves 5.84 kg on a 0.04% input change. Phase 2 has to actually re-run at
0.3289.
