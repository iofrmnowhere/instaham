# Phase 1.1 — The rebuilt manifest lost the segmentation scale ladder

Status: closed — F50 closed and verified on device with a measured envelope; F51 implemented
and verified against the current manifest

Opened as a subphase of phase 1 rather than a phase of its own because it was introduced by
phase 1's own manifest regeneration and has to be undone before phases 2 and 3 can measure
anything. Numbering continues at **F50**.

## Symptom

With phase 1's fix applied (`capabilities.weight.available` back to `true`) the freeze is
gone, but the weight branch now reports unavailable after analysis with a message about the
pig outline not being detected. The wording the user saw matches
`run_and_persist_pipeline_use_case.dart:467`, the `mask_implausibly_small` case: "the pig
outline could not be detected properly in this photo -- only a small fragment was found."

This attribution is **inferred from the message text, not confirmed from an envelope.** It is
the strongest match of the reasons now reachable, and the other candidate is ruled out below,
but no envelope has been read from the device.

## Root cause

### F50 — `capabilities.segmentation.input_scale` is absent from the rebuilt manifest

`HEAD` (`e13b1f4`) carries the block:

```json
"input_scale": {
  "cm_per_px": 1.10,
  "ladder_multipliers": [1.0, 1.32, 1.68, 0.77],
  "retry_conf_threshold": 0.10
}
```

The working-tree `assets/ml/manifest.json` rebuilt during phase 1 does not contain
`input_scale` at all. The regeneration ran `ML.export.build_manifest` against the staged
fragments in `build/ml_export/`, and the staged **segmentation** fragment predates
`ML/export/export_yolo.py:130`, which still emits `input_scale` today. Only the weight
fragment was re-exported; the other three were reused as staged, so the segmentation
capability was silently rolled back to a pre-F18/F19 shape.

The consequence chain is mechanical:

1. `manifest.cpp:213` only reads `input_scale` when the key is present; absent, it leaves
   `input_cm_per_px` at its `0.0` default and `scale_ladder_multipliers` at the single-rung
   `{1.0}` default (`manifest.h:50`, `manifest.h:56`).
2. `pipeline.cpp:307` computes `scale_aware` as `cm_per_px != nullptr && ... &&
   manifest.segmentation.input_cm_per_px > 0.0`. With the manifest value at `0.0` this is
   false no matter how good the user's reference object is.
3. `pipeline.cpp:324` therefore pushes a single plain whole-frame letterbox attempt, so F19's
   retry ladder — the mechanism whose entire purpose is to re-segment at a larger content
   scale when the first mask comes back too small — never runs.
4. `pipeline.cpp:571` then applies F23's raised `min_mask_diagonal_fraction` of `0.35` to
   whatever that one attempt produced, and emits `mask_implausibly_small` when it falls short.

So the gate that was raised to `0.35` on the assumption that the ladder would rescue small
masks is now being applied with the ladder disabled. That is a plausible mechanism for a
genuine pig photographed from a normal working distance to be rejected as "only a small
fragment was found."

### Why this is not the other "pig outline" message

`run_and_persist_pipeline_use_case.dart:411` also mentions the pig outline, but it is reached
only when `weight.reason == 'weight_pending_field_validation'`. In `pipeline.cpp` that reason
lives in `weight_unavailable_json`, which every branch assigns only on the `weight_override ==
false` side of its ternary. With `weight.available` now `true` and `assets/ml/weight/
xgboost.onnx` hashing to the value the manifest declares (verified), `weight_override` is true
and that reason is unreachable. The message the user saw cannot be that one.

### F51 — a staged fragment older than its exporter regresses silently

`build/ml_export/` is gitignored (`.gitignore:33`), so the fragments `build_manifest` consumes
are untracked build output that can be arbitrarily old, while the exporter that would produce
them is versioned. Rebuilding the manifest to change one capability therefore silently reverts
every other capability to whatever its stale fragment last said, with no warning and no diff
the author is looking at — the weight change was the intent, and the segmentation rollback
rode along invisibly.

`build_manifest --check` exists and is described as a CI determinism gate that re-runs the
export and diffs sha256s. Whether it would have caught a missing *block* (as opposed to a
changed hash) has not been checked.

Incidental to the same rebuild: `bundle_id` moved from `instaham-ml-9781c14` to
`instaham-ml-e13b1f4`, and the file was reindented from 1-space to 2-space. Both are the
canonical builder's own output, not hand edits, and neither is a defect — but they are why the
diff against `HEAD` is ~600 lines for what was meant to be a one-value change.

## Change made

**F51 implemented as the recommended key-loss guard**, in `ML/export/build_manifest.py`:

- `_key_paths()` — walks a manifest dict to a flat set of dotted key paths (lists are leaves,
  not recursed into: their positional entries carry no stable identity to diff against).
- `_check_no_key_loss()` — before `build()` writes, loads the existing `assets/ml/manifest.json`
  (no-op if it doesn't exist yet), diffs its key paths against the newly assembled manifest's,
  and raises `SystemExit` naming every dropped key if any exist. Changed values are untouched
  by this check; only outright disappearance trips it — exactly the shape F50 was.
- `build()` gained `allow_key_removal: bool = False`; the CLI gained `--allow-key-removal` for
  a deliberate drop.
- `--check`'s module docstring corrected from "CI determinism gate (re-run export, diff
  sha256s)" to "CI staleness gate (re-hash model/regressor/class_map files against the
  manifest)" — it does not re-run exporters or catch a missing key, as documented above.

Verified with a standalone script (not committed) against the live `assets/ml/manifest.json`:
the identical manifest passes with no error; a manifest with
`capabilities.segmentation.input_scale` removed raises `SystemExit` naming the four dropped
paths (the block itself plus its three children); `--allow-key-removal`-equivalent
(`allow_key_removal=True`) passes the same removal through with a printed notice. No
`build/ml_export/` fragments exist in this environment, so the full `build()` call path with
real fragments was not exercised — only `_key_paths`/`_check_no_key_loss` directly.

## Steps

- [x] **F50 — restore `input_scale` to the segmentation capability.** Taken as a **hand edit**,
      not a re-export: `ultralytics`/`torch` installation into the scratch export venv was
      still running when this was picked up, and the three values are pinned constants with no
      new derivation needed — `cm_per_px: 1.10`, `ladder_multipliers: [1.0, 1.32, 1.68, 0.77]`,
      `retry_conf_threshold: 0.10`, copied verbatim from `HEAD`'s
      `capabilities.segmentation.input_scale`, inserted in `assets/ml/manifest.json` between
      `postprocess` and `protocol_version` (`HEAD`'s own key order). Verified by loading both
      `HEAD`'s and the working tree's `capabilities.segmentation` as JSON and comparing equal
      — they now match exactly. Recording this here so a future manifest regeneration from a
      stale `build/ml_export/segmentation/` fragment does not silently drop it again (F51 is
      the standing fix for that class of trap, still open below). `weight.available` was left
      untouched at `true` from phase 1.
- [x] **F50 — confirm the fix on device.** Confirmed by the user on a real device: the weight
      branch no longer reports unavailable after analysis, so the `mask_implausibly_small`
      rejection is gone with the ladder live. The contingency below it did not fire — the
      `0.35` threshold is not, on this evidence, rejecting a normally framed pig once F19's
      retry ladder is enabled. This is an observation of the user-facing outcome, not an
      envelope read; the exact `mask_diagonal_fraction` is still owed by the next step.
- [x] **F50 — capture the envelope, not just the message.** Captured from a real device run
      on 2026-09-07 (`scan_hm2nkeb6se_iaainz`, reference photo
      `.pig_pictures/92kg_pig_meter_stick.HEIC`, true weight 92 kg); the raw logcat paste is
      `docs/logs/adb_log.md`. Reading the persisted scan turned out to be impractical on a
      release build — `adb run-as` is unavailable, so a temporary chunked `INSTAHAM_ENVELOPE`
      dump was added to `run_and_persist_pipeline_use_case.dart` instead and is to be removed
      once this subphase closes. The measured values are in Verification below. The
      correction to the earlier note here: the gate's measured fraction is published under
      `construction.mask_diagonal_fraction` (`pipeline.cpp:441`) on the success path, not
      under `weight`, which carries it only on the rejection path (`pipeline.cpp:592`).
- [x] **F51 — decide whether `build_manifest` should refuse a stale fragment.** Options are to
      have it compare each fragment against a re-run of its exporter (what `--check` may
      already do), to stamp fragments with the exporter version that wrote them and warn on a
      mismatch, or to accept the hazard and require a full four-capability re-export for any
      manifest change. Doing nothing leaves the same trap armed for the next single-capability
      edit.

      **`--check` is now read and does not close this.** `ML/export/build_manifest.py:82`
      re-hashes only the `model`, `regressor` and `class_map` entries of each capability
      against the staged files. It never re-runs an exporter, so its module docstring's
      "CI determinism gate (re-run export, diff sha256s)" overstates it. A vanished
      `input_scale` block changes no file hash, so `--check` passes clean through exactly the
      F50 defect. Re-running the exporters is also not a usable option here for the reason
      F50 already hit: `export_yolo.py` needs `ultralytics`/`torch`, absent from the export
      venv, so any design that validates a fragment by regenerating it blocks every manifest
      edit on a heavy environment.

      **Implemented: a key-loss guard in `build()`.** Before writing, it loads the existing
      `assets/ml/manifest.json` and fails if any key path present there is absent from the
      newly assembled manifest; changed values pass untouched, since disappearance is the
      signal this class of bug emits. An `--allow-key-removal` escape hatch covers a
      deliberate drop. See Change made below. The `--check` docstring was corrected in the
      same change.

## Verification

- `assets/ml/manifest.json` contains `capabilities.segmentation.input_scale` with the three
  `HEAD` values, and `git diff` against `HEAD` for the segmentation capability is empty.
- **Satisfied — the scan produces an estimate rather than a rejection.** `weight.status` is
  `ok` with `estimated_kg` 87.36 and no `reason` field at all; `segmentation.status`,
  `construction.status`, `cutter.status`, `health.status` and `view.status` are likewise all
  non-failing. The `mask_implausibly_small` path is not reached.
- **Satisfied — `mask_diagonal_fraction` is 0.6343** on
  `.pig_pictures/92kg_pig_meter_stick.HEIC`, against the `0.35` minimum. The margin is 1.81x,
  so on this photo F23's raised threshold is not marginal, and the ladder is not what carries
  it: `ladder_rung` is 0 and `rungs_tried` has a single entry, meaning the first attempt
  already cleared the gate and the loop exited without a retry.

### What this measurement establishes for phase 2

The restored block is demonstrably being read, not merely present: `input_cm_per_px_used` is
`1.1`, which is `segmentation.input_scale.cm_per_px` times rung 0's `1.0` multiplier. Had
`input_scale` still been missing, `scale_aware` would be false and this field would be `0.0`.
That is the direct evidence F50 was the right diagnosis.

The scale block from the same run is the input phase 2 was waiting on:

| field | value |
| --- | --- |
| `cm_per_px_actual` | 0.06443 |
| `cm_per_px_target` | 0.35 |
| `k` | 0.18410 |
| `height_ratio` | 0.66431 |
| `implied_camera_height_m` | 1.2489 |
| `training_camera_height_m` | 1.88 |
| `estimated_kg` | 87.36 (true 92, error -4.64 kg / -5.04%) |

Two observations phase 2 should start from rather than re-derive:

1. **`k` is exactly `cm_per_px_actual / cm_per_px_target`** (0.06443 / 0.35 = 0.18410), so
   swapping the target to 0.3289 raises `k` to 0.19591, a 6.4% larger linear resampling and a
   13.2% larger normalized mask area. The direction is therefore knowable without a rebuild:
   0.3289 makes every area feature larger. Whether that moves `estimated_kg` up by enough to
   close a 4.64 kg shortfall is not knowable without a rebuild, because the regressor is an
   XGBoost ensemble over 16 features and not monotone in area by construction.
2. **The single-photo error sign is consistent with 0.3289 being the better target**, since
   the estimate is low and the change would enlarge the mask. This is one photo against one
   known weight; it is a hypothesis for phase 2's three-photo run, not a result.
