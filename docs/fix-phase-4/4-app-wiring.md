## Symptom

Phases 1 to 3 live in the host harness and the manifest. The app still runs the old path —
`packages/instaham_ml_ffi/src/pipeline.cpp` contains no reference to `input_scale_mode` or
`normalize_first` (F64). This phase is where the README's pipeline first runs in the app.

## Root cause

Not a defect. This phase carries a host-validated change onto the device.

## Change made

1. Make `pipeline.cpp` run the README's composition. Phase 1.1 leaves exactly one segmentation
   input path, so there is no mode to flip — the work is that `pipeline.cpp` calls it, passes
   `cm_per_px_target` as the normalization scale, applies the inverse canvas and rotation
   transforms in README §8's order, and surfaces the §6 halt as a declared weight-branch failure
   rather than a crash or a silent retry.
   Any manifest field phase 3 renamed or removed is regenerated by re-running
   `ML/export/export_yolo.py` and `ML.export.build_manifest`. **Never hand-edit
   `assets/ml/manifest.json`** — see the changelog's 2026-09-14 entry for the trap that closes.
2. Confirm the Dart side needs no change. EXIF orientation is already normalized once at capture
   time on the Dart side, and the native layer performs no rotation by contract
   (`packages/instaham_ml_ffi/src/include/instaham_ml.h:98-101`,
   `src/util/image_io.h:17-18`). The new path's rotation happens inside native composition and
   is undone before the mask leaves it, so the contract holds. Verify this rather than assume
   it: if anything in the new path returns a mask in rotated orientation, the contract is broken
   and the phase stops.
3. Check AGENTS.md rule 6 explicitly. The reference endpoints are persisted in original-capture
   coordinates by `reference_marking_screen.dart` and are consumed only as the scalar
   `cm_per_px_actual`, which is invariant under both the uniform resize and the rotation. Record
   that reasoning in the phase; it is the rule most likely to be raised against this change.
4. Confirm the envelope fields the UI and the logs already read still exist and still mean the
   same thing on the new path, or update both together.

## Verification

- `dart format` on any changed Dart files, `flutter analyze`, and targeted `flutter test` on the
  changed behaviour. Report the exact commands and anything that could not run.
- Build the APK and sideload it onto the physical phone. That is how this project tests
  native/ML changes; there is no attached emulator or device in the development environment.
- Re-run the same field captures used in phase 2 on device and compare the envelope against the
  host numbers. A host-device disagreement on the normalized dimensions, the rotation flag, the
  canvas offsets or the mask area is a blocker, not a rounding note.
- **Detection rate is watched here, not gated here.** Phase 1.1 removes the round-4 retry ladder
  per README §13, and this is the first run that would show a regression from that. If detection
  drops, record it and raise it to the user as a flag; do not reinstate the ladder inside this
  phase.
- **Expect README §6's halt to fire** on full-resolution captures (F61: 4032x3024 normalizes to
  764x573 against a 540 bound). That is the specified behaviour, not a bug in the wiring. Record
  how many captures halt and at what dimensions — that is the evidence the user needs to rule on
  the open flag.
- Record the device results in a durable document as each run completes.
