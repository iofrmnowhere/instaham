# Phase 1.1 — Make the README path the only path

Status: not started

Parent: [`../fix-4.md`](../fix-4.md). Authority:
[`INSTAHAM_APP_WEIGHT_PIPELINE_SCALING_ROTATION_FIX_README.md`](../../INSTAHAM_APP_WEIGHT_PIPELINE_SCALING_ROTATION_FIX_README.md)
sections 2 to 8 and 13, implemented as written.

Opened 2026-09-19 after the user overruled phase 2's REJECT verdict and instructed that the
README be brute-forced rather than evaluated. This phase does not rewrite phase 1's arithmetic —
`decide_normalize_first_composition()` in `stages/canvas_scale.h` and the composition block at
`stages/segmentation.cpp:79-114` are correct and stay. It removes the three structural hedges
phase 1 wrapped around them.

## Symptom

The README's pipeline exists in the source tree and cannot run. It is selected by a manifest
field that defaults to the old behaviour, it is consulted only from the host CLI, and where it
does run it is wrapped in two behaviours the README forbids.

## Root cause

F64, stated in the parent document. Not an arithmetic defect — a shipping defect. Three
specific hedges:

1. **The mode switch.** `SegmentationInputScaleMode` (`manifest.h:41`) offers `kCanvasScale`
   and `kNormalizeFirst` and defaults to `kCanvasScale` (`manifest.h:75`). The README describes
   one pipeline, not a choice between two.
2. **The retry ladder.** README §13 is a single segmentation pass at one scale. The ladder at
   `pipeline.cpp:329-360` is a multi-rung search, and §15 lists re-scaling the normalized image
   among the things not to do.
3. **The F61 oversize fallback.** Phase 1 added canvas enlargement inside
   `decide_normalize_first_composition()` where README §6 requires a halt.

## Change made

### 1. Retire the mode switch

Make the normalize-first composition the only composition. Concretely:

- Delete `SegmentationInputScaleMode` and `SegmentationCapability::input_scale_mode` from
  `manifest.h` / `manifest.cpp`, and the branch at `stages/segmentation.cpp:79`.
- Delete the `kCanvasScale` composition body and, once nothing calls it, the
  `canvas_scale.h` helpers that exist only to serve it. Check `test_segmentation_canvas.cpp`
  and `ML/host_scale_test/weight_branch_cli.cpp` for callers before deleting anything.
- `capabilities.segmentation.input_scale.cm_per_px` no longer means a presentation scale. On
  this path the normalization target is the weight capability's `cm_per_px_target`. Phase 3
  decides whether the segmentation field is removed or renamed; **this phase must not leave two
  fields that could each plausibly be the scale.**
- Keep `SegmentationOutput::used_normalize_first` for one release as an envelope field that
  always reports `true`, so a stale build is identifiable from an envelope alone, then let
  phase 5 fold it into the debug block.

Do not change the default and leave the old code reachable. A dead branch behind a removed
switch is the same hedge in a different shape.

### 2. Remove the retry ladder from this path

README §13 runs one pass. Remove the ladder from the weight branch's segmentation call, along
with the per-rung bookkeeping that only the ladder consumed. Detection failure becomes a single
declared failure with a reason, not a rung escalation.

Two things must survive the removal, because they are not the ladder:

- the `clamped_to_letterbox` reporting field, if it still describes something real on the new
  path — verify, and remove it too if it does not;
- whatever the health branch uses, if it shares this code. **Check before deleting.** AGENTS.md
  rule 4 requires the health branch stay independent of the weight branch, so a ladder removal
  that silently changes health-branch detection is a defect introduced by this phase.

Record in the phase that the ladder was added in round 4 for F18/F19 (detection failed without
it), that its removal here is by instruction, and that phase 4's device run is the first place a
regression would surface. That is the flag, not a reason to keep it.

### 3. Ship README §6's halt

Replace the oversize fallback in `decide_normalize_first_composition()` with the README's
behaviour: if `rotatedWidth > 960` or `rotatedHeight > 540`, the composition fails and the
weight branch declares a failure carrying both the normalized dimensions and the canvas bound.
Never shrink the normalized image — README §15 and the whole point of `cm_per_px_target`.

**This will fire on ordinary captures.** F61's worked example is a 4032x3024 capture at
`cm_per_px_actual ≈ 0.0644`, which normalizes to 764x573 against a 540 bound. Implement the halt
anyway, give it a distinct machine-readable reason so it is never confused with a detection
failure, and make sure the failure text names the two dimensions and the bound. The question of
whether captures should be downscaled before normalization is raised as an open flag in the
parent document and is not answered here.

### What does not change

The mask-to-training-space transform (round 7's F55) is unchanged and becomes a no-op with
`k = 1.0` by construction. Quality gates keep their position before Ji-Duan. The cutter, the 16
`chen16_noheight` features, the feature order and the XGBoost model are untouched. The rotation
rule stays exactly README §4's: rotate 90° clockwise when `normalizedHeight > normalizedWidth`,
never counterclockwise, no dynamic head inference.
