# Metrics plan phase 4.1 — remove scenario 7; keep scenario 5's `reject` as shipped

Status: **planned, not started.** Subphase of the completed phase 4. Runs before phase 5.

Scope is two decisions taken on 2026-09-12, both about the scenario corpus only. No `lib/`
production change, no model change, no manifest change.

1. **Delete scenario 7** (`07_multiple_pigs_composite`) from the fixture corpus and the
   functional suite.
2. **Keep scenario 5 exactly as it is** — asserting the view classifier's `reject` output —
   and record that as a deliberate, closed decision rather than an open question.

## Why

### Scenario 7 asserts nothing the suite does not already cover

Scenario 7 was created for `INSTAHAM_APP_REQUIREMENTS_AFTER_TRAINING.md` §14 bullet 7
(multiple-pig image). Phase 4 task 1's run showed it cannot exercise that bullet:

- The view classifier returns `reject` at 0.9614 confidence, so the envelope stops at the
  view stage. Segmentation never runs, and mask selection — where §7 check 1 ("exactly one
  usable pig instance") actually lives — is never reached.
- There is no live `multiple_pigs` reason code to assert against. `WeightEligibilityChecker`,
  which owns it, is unreferenced by the shipped pipeline (finding 5, restated in phase 4
  task 3's audit). The persisted reason is `view_rejected`, the same code scenario 5 already
  asserts.

So the two things scenario 7 does prove — a real multi-pig frame is withheld, and the
`multiple_pigs` code is dead — are respectively a duplicate of scenario 5 and a fact better
carried in prose than in a test that looks like it covers a capability it does not.

Exercising §14 bullet 7 properly would need a frame with **two pigs both in valid dorsal
framing**, so the view gate passes and mask selection is actually put under test. No such
photo exists in `.pig_pictures/` or `health_pigs/`, and this subphase does not ask for one
to be collected.

### Scenario 5's `reject` is correct and stays

Phase 4 task 2 restated scenario 5 against its observed run: view label `reject` at 0.9968,
`dorsal_valid` 6.7e-06, `health_only` 0.0032; envelope status `stopped`, reason
`view_rejected`; both branches withheld.

This matches the shipped app exactly, at two call sites:

- `lib/features/capture/presentation/screens/capture_screen.dart:364` — sets
  `ScanStatuses.rejected` at capture time.
- `lib/features/inference_pipeline/domain/use_cases/run_and_persist_pipeline_use_case.dart:72`
  — writes both branches ineligible, sets status `rejected`, returns early.

`reject` is therefore a live, user-visible app state, not a test-only artifact. Round 17's
handoff left "should scenarios 5/7 also change?" open on the assumption that the app has no
reject state; that assumption does not hold against the code above, and this subphase closes
the question as **no change to scenario 5**.

Noted but explicitly not acted on here: the classifier rejecting a genuine side-on capture
means a lateral photo — a reasonable input for skin and lesion assessment — is thrown out
for health too, not only for weight. Whether that routing is right is a **model and product
question**, not a fixture question. It is recorded in "Deferred" below.

## Accepted gap

After this subphase, `INSTAHAM_APP_REQUIREMENTS_AFTER_TRAINING.md` §14 bullet 7
(multiple-pig image) has **no fixture and no test**. This is a deliberate reduction in
claimed coverage, chosen over keeping a test whose name promises multi-pig handling while
asserting only a view rejection. It joins the two §14 gaps already accepted: no third
reference object of a distinct length, and no real lesion close-up.

State it as a gap wherever coverage is reported. Do not describe the remaining suite as
covering all of §14.

## Deferred, not part of this subphase

- Sourcing a two-pig dorsal frame to cover §14 bullet 7 properly.
- `test_feature_domain.exe`'s `STATUS_STACK_BUFFER_OVERRUN` crash, still open and unexplained.

## Plan rating: 8/10

**Pros.** Small, fully reversible, touches no production code and no model. It removes a test
that overstates what it verifies, which is a net honesty gain — a suite that looks like it
covers multi-pig handling is worse than one that openly does not. Scenario 5's decision is
settled against the actual shipped code at two verified call sites rather than against an
assumption. Task 2's byte-identical regeneration check catches the usual failure mode when a
generated corpus is edited by hand.

**Cons.** Claimed §14 coverage goes down, and the corpus loses its only real multi-pig
photo — if bullet 7 is ever covered properly, that image has to be re-sourced. The deferred
side-on routing question is the more consequential finding, and this subphase does not
advance it. Several documents reference scenario 7 in historical context
(`docs/metrics-phase/3-fixture-corpus.md`, `3.1-corpus-rebuild.md`); those are left as
historical record, so a reader who greps for "scenario 7" will still find hits and must
check dates.
