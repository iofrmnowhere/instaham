# Metrics plan subphase 6.2 — recorded device results, and two measurement defects

Status: **planned, not executed.**
Parent: `docs/metrics-phase/6-device-metrics.md` (task 3, task 4).
Sibling: `docs/metrics-phase/6.1-benchmark-fixture-asset.md`.

This subphase does two things. First, it makes the one executed Test Lab run's numbers
durable, because on the Spark free tier a lost measurement costs a scarce, approval-gated run
to recover. Second, it fixes two defects in *how* metrics 2 and 3 are measured — both found by
reading the executed test, not by re-running it.

Neither defect is a pipeline bug. The pipeline did what it does; the test measured the wrong
thing and labelled it confidently. No `lib/` change, no model change, no manifest change and
no native change is proposed here. The whole subphase lives inside
`integration_test/benchmark_test.dart` plus the two documents that quote its numbers.

## Defect A — metric 3 measures post-inference RSS, not startup

`integration_test/benchmark_test.dart:107` declares "Metric 3 — Memory footprint during app
startup" and reads `ProcessInfo.currentRss` at line 115. Phase 6's disposition table and its
"Agreed targets" note both fix the scope of metric 3 to **startup** memory, narrower than the
metric's original "peak inference" name, and specifically say the test already measures
startup so no change of measurement point is needed.

That was true when metric 2 was a `markTestSkipped` placeholder. It stopped being true when
task 3 wired metric 2 to the real pipeline.

All three `testWidgets` cases share one process, and `integration_test` executes them in
declaration order: metric 1 (line 20), metric 2 (line 72), metric 3 (line 107). By the time
metric 3 reads RSS, metric 2 has constructed `MlRuntime`, loaded all four ONNX models, and run
ten complete pipelines. The 1446.6 MB therefore includes every model's weights, the native
session arenas, and whatever the ten runs did not release. It is a real number about a real
process; it is simply not the number the metric's name claims.

There is a second, smaller point hiding inside the first. 1446.6 MB is large next to a 68 MB
model bundle. Whether that is ordinary session and arena residency or growth across the ten
iterations cannot be told from a single end-of-run reading, and the difference matters — one is
a fact about the models, the other is a leak.

### Options

**Option A1 — reorder, and take both readings (recommended).** Move metric 3's declaration
above metric 2's, so RSS is read after `App()` has been pumped and settled but before any model
is loaded. That reading genuinely is startup memory, which is what the metric claims and what
phase 6 agreed. Then print a second RSS reading at the end of metric 2 under a distinct key, so
the post-inference figure is kept rather than thrown away — the 1446.6 MB above stops being a
mislabelled number and becomes a correctly labelled one.

Cost: a block move plus two `print` lines. No extra device time, no extra Test Lab run beyond
the one that will re-measure everything anyway, and no production change. It yields strictly
more information than today: a startup figure the metric can honestly own, and a peak figure
that is the more useful number for a phone with limited RAM.

The cost is a real but manageable fragility: the measurement now depends on declaration order,
which is an implicit contract. It must be stated in a comment at both sites so a future
reordering does not silently re-break it.

**Option A2 — rename only.** Keep the ordering and retitle the metric to "memory footprint
after inference", updating phase 6's disposition table and `docs/device-testing-plan.md`'s
reporting template to match. Zero risk, and it makes the existing 1446.6 MB honest
retroactively, but it abandons the startup figure that phase 6 agreed to, and startup memory is
the number that predicts whether the app survives on a low-RAM device.

**Option A3 — a separate integration test entry point.** Put metric 3 in its own file so it
gets a clean process. This is the only option that gives a perfectly uncontaminated startup
reading. It is also the expensive one: a second `-Ptarget` build, a second APK, and a second
Test Lab invocation, which on a 5-runs-per-day cap is a real cost for a report-only metric with
no threshold attached. Not worth it while metric 3 is report-only.

**Recommendation: A1.** Revisit A3 only if metric 3 ever becomes a gate.

## Defect B — metric 2 has no warm-up, and its "P95" is the maximum

Two separate problems in the same loop at `integration_test/benchmark_test.dart:84-89`.

**No warm-up.** `MlRuntime.instance()` is awaited before the loop, but the first `runPipeline`
call is inside the timed region. Whatever that first call does once and never again — asset
staging to the filesystem, native ORT session creation, arena allocation, first touch of the
model weights — is charged to iteration 0 and enters the sample. With ten iterations a single
inflated first value drags the median by up to half a position and sets the maximum outright.
Until one run is excluded, it is not possible to say how much of the ~17 s median is inference
and how much is one-time setup.

**The percentile index degenerates at N = 10.** The expression is
`elapsedMs[((elapsedMs.length - 1) * 0.95).round()]`. At `length == 10` that is
`(9 * 0.95).round()`, which is `8.55.round()`, which is `9` — the last index of a sorted
ten-element list. The printed `INFERENCE_P95_MS: 20071` is therefore the slowest of ten runs,
which, given the first problem, is very likely the unwarmed first run. It is labelled as a
percentile in the test, in the logcat key, and in every document that quotes it.

Ten samples cannot support a 95th percentile under any indexing scheme. The honest options are
to report what ten samples can support, or to take more samples.

### Options

**Option B1 — warm up, keep N = 10, report median and maximum (recommended).** Add one
discarded call before the loop, and rename the second statistic to `INFERENCE_MAX_MS`. Ten
timed runs at roughly 17 s is about 170 s; plus one warm-up run and the other two metrics, the
suite lands near 200 s — comfortably inside the 5-minute Test Lab timeout the runbook uses,
with room for the slower `lion` tier. Honest, cheap, and it does not touch the run command.

**Option B2 — warm up and raise N to 20 for a real P95.** With nearest-rank indexing,
`ceil(0.95 * 20) - 1` is index 18, a defensible 95th percentile. The arithmetic is the easy
part; the schedule is not. Twenty timed runs plus a warm-up is roughly 357 s on `oriole` alone,
before metrics 1 and 3, which overruns the 5-minute timeout and would need `--timeout` raised
on the run command and re-verified per tier. On the low-end `lion` the same loop could be
substantially longer again.

One quota consequence is worth stating plainly: a three-device matrix consumes three of the
day's five physical runs regardless of duration, so a longer matrix does not cost more runs —
but a timeout misjudged upward costs a whole matrix, and with it most of a day's budget.

**Recommendation: B1 now, B2 only if metric 2 becomes a gate.** Phase 6 leaves metrics 2 and 3
report-only precisely because no baseline exists, and a number that gates nothing does not
justify a six-minute-per-device run.

**Optional, cheap, and separately valuable:** print RSS once per iteration inside metric 2's
loop under a distinct key. It costs one syscall per run and no extra device time, and it
answers the leak-versus-residency question raised under defect A directly — a flat series is
model residency, a rising one is growth. Flagged as optional because it widens metric 2's scope
beyond latency; take it or leave it as a deliberate call, not by accident.

## Open questions

1. **Is 1446.6 MB residency or growth?** Unanswerable from one end-of-run reading. The optional
   per-iteration print settles it at no measurable cost, and the answer decides whether this is
   a reporting fix or the start of a leak investigation.
2. **Does metric 1's 68 ms margin survive the low tier?** Answered, and badly: `lion` misses by
   2799 ms, `a04s` by 6558 ms. Not a margin question any more — see Finding 3.
3. **Do metrics 2 and 3 get thresholds after a clean three-tier run?** The blocking half is
   answered: round 4's `lion` run completed, so a full three-tier set of real numbers now
   exists (see Finding 5's table). The thresholds themselves are still unset, and setting
   them now means deciding what to do about a 70 898 ms low-tier median — a product decision,
   not a measurement one.
4. **Can metric 2 be measured on entry-level hardware at all with `inferenceRuns = 11`?**
   Answered for `lion`: yes, at `--timeout 15m`, with 96 s of headroom (Finding 4). Still open
   for hardware slower than `lion` — `a04s` timed out at the same budget. If a device slower
   than `lion` must be covered, a lower `inferenceRuns` for that class or a lighter metric 2
   variant is still the likely path.
5. **Why is `lion`'s post-inference RSS less than half the mid and high tiers'?** New, from
   Finding 6. 682.6 MB versus ~1500 MB from the same pipeline and fixture, with comparable
   startup RSS. Needs an answer before any memory threshold is set, since the current numbers
   would reward the slowest device.

**Cons.** Nothing here is verified on hardware, so the corrected metric 3 and the warmed metric
2 remain predictions until an approved run turns them into observations — this document proposes
measurements, it does not produce them. The recommended metric 3 fix trades one fragility for
another: declaration order becomes load-bearing, enforced by a comment rather than by anything
mechanical. Option B1 accepts that ten samples yield no percentile at all and settles for a
maximum, which is honest but weaker than what the metric's name promised readers. And the whole
subphase improves two metrics that gate nothing, while the largest known problem in the project
— the view classifier rejecting genuine side-on captures, so a lateral photo gets no health
assessment — still has no phase of its own.
