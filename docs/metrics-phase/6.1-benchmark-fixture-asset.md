# Metrics plan subphase 6.1 — how the benchmark image reaches the device

Status: **planned, not executed.** Blocks phase 6 task 3 (metric 2).
Parent: `docs/metrics-phase/6-device-metrics.md`.

This is a **decision subphase**. It resolves one question and writes down the answer; the
code it unblocks belongs to phase 6 task 3, not here.

## Why this exists

Phase 6 task 3 says metric 2 should "load a fixture image from `test/fixtures/scenarios/`,
run the full pipeline N times". That instruction cannot be followed as written, and the
reason was not visible when the phase was planned.

`test/fixtures/scenarios/` is a host test path. It is not part of the Flutter asset bundle,
so none of it exists inside an APK. An integration test running on a real phone has no
access to it. The native pipeline also takes a **filesystem path**, not an asset key
(`MlRuntime.runPipeline`, `lib/services/ml/ml_runtime.dart:151`), so whatever route is
chosen must end with a real file on the device filesystem.

The obvious fix — add the image to the `pubspec.yaml` asset list — conflicts with phase 6's
own opening promise: "No `lib/` production change. No model change. No manifest change."
Putting an 873 KB photograph of a real farm pig into every shipped APK is a production
change, and one that ships test data to end users. That is a decision for the project owner,
not a detail to be settled inside a task.

## The image in question

The candidate is scenario 01, the fully valid dorsal capture:

| field | value |
|---|---|
| path | `test/fixtures/scenarios/01_valid_dorsal_100cm_reference/image.jpg` |
| size | 873 461 bytes (853 KB) |
| origin | `.pig_pictures/92kg_pig_meter_stick.HEIC`, real field capture |
| recorded weight | 92.0 kg |
| transform | EXIF-upright, longest side resized to 1600 px, JPEG q90 |
| expected outcome | `dorsal_valid`; weight branch produces a number; health branch assessed |

It is the right image for a latency measurement precisely because it passes every gate. A
fixture that trips a quality or eligibility check short-circuits the pipeline, so its timing
would under-report the real cost — the weight branch would never run. Scenario 02 (96 kg,
Porac stick, 786 KB) is an equally valid alternative; scenario 01 is the better-documented of
the two.

**Do not shrink the image to save space.** Resizing changes how much work segmentation and
the downstream stages actually do, so a smaller image would produce a latency number that
does not describe a real capture. The 853 KB is the honest cost of measuring the real thing.

## Options

### Option A — push the file at run time, no APK change (recommended)

Firebase Test Lab can place arbitrary files on the device before the test starts, via
`--other-files` with a `DEVICE_PATH=FILE_PATH` pair. Verified present in the installed
`gcloud` (SDK 578.0.0). The flag's own help restricts device paths to `${EXTERNAL_STORAGE}`
or `${ANDROID_DATA}/local/tmp`. The local equivalent for a phone on USB is a plain
`adb push` to the same path, so the test code is identical in both environments.

- **Keeps every phase 6 promise.** No `pubspec.yaml` change, no production asset, nothing
  extra in a shipped APK, no test data reaching end users.
- **The fixture stays where it belongs**, in the test corpus, with its `meta.json` provenance
  next to it.
- **Main risk, and it must be settled before the plan is called done:** scoped storage. The
  app declares only `CAMERA` (`android/app/src/main/AndroidManifest.xml:2`). On API 30+ an
  app cannot freely read arbitrary `/sdcard` paths, and on API 33+ (`tokay` is API 35) media
  reads want `READ_MEDIA_IMAGES`. `${ANDROID_DATA}/local/tmp` — that is `/data/local/tmp` —
  is the more likely readable location, but it is not guaranteed across all three device
  tiers.
- **Mitigation available at zero production cost:** `android/app/src/debug/AndroidManifest.xml`
  already exists and already adds a debug-only permission (`INTERNET`). A read permission
  added there applies to the debug APK that Test Lab runs and never to release.
- If the test cannot read the pushed file, the test must **fail with the path and the error**,
  not silently skip. A skipped metric 2 after a Test Lab run wastes quota.

### Option B — bundle the image as a normal Flutter asset

Add `assets/benchmark/pig_dorsal_92kg.jpg` to the `pubspec.yaml` asset list; the test reads it
through `rootBundle` and writes it to a temp directory before calling the pipeline.

- Simple, works identically on every device and on a local `flutter test`, no storage
  permission question at all.
- Costs +853 KB in every APK forever, on top of the 68 MB `assets/ml` bundle.
- Ships a photograph of a real pig, taken at a real farm, to every end user. There is no
  consent question for a latency benchmark specifically, but it is still test data in a
  production artifact.
- **Flutter has no conditional asset bundling.** `pubspec.yaml` assets are global; the
  `android/app/src/debug/` source set cannot hold Flutter assets, because they are compiled
  into `flutter_assets` from `pubspec.yaml` and not from Android source sets. Making this
  debug-only would require a full build flavor, which means editing `android/`, which
  AGENTS.md discourages and which is far more change than the metric is worth.

### Option C — synthesize an image in the test

Generate a solid-colour or noise JPEG at run time.

Rejected. It is not a real capture, so segmentation finds no pig, the pipeline stops at a
gate, and the measured time describes nothing. It would produce a green test and a
meaningless number, which is worse than no number.

## Recommendation

**Option A**, with the scoped-storage question resolved before any Test Lab quota is spent.
It is the only option that leaves the production APK untouched, and the local `adb push` path
means the whole thing can be proven on one phone over USB at no Firebase cost.

Fall back to option B only if the pushed file turns out to be unreadable on any of the three
device tiers even with a debug-only read permission. If that happens, record the fall-back
and its APK cost here rather than quietly editing `pubspec.yaml`.

## Prerequisite that applies to either option

`test/fixtures/` is currently **untracked in git** — the whole corpus, including this image.
Option B would make `pubspec.yaml` reference a file that does not exist in a clean checkout,
which breaks the build for anyone else and for CI. Option A is safer here too, since the path
appears only in a command line, but a missing fixture still means an unrunnable benchmark.

Either way, the fixture corpus needs to be committed, or the benchmark image specifically
does, before this is relied on. That is noted as a dependency, not solved here.

## Validation

This subphase produces no Dart code, so there is nothing for `flutter test` to run. Its
validation is the `adb push` plus read-back check on a USB-connected phone, which costs no
Firebase quota. `flutter analyze` applies only if the debug manifest is touched, and a
manifest change is checked by building the debug APK, not by the analyzer.

No Firebase Test Lab run is submitted under this subphase. The parent phase's task 4 remains
the only step that spends quota, and it stays gated on explicit approval.

## Open questions

1. **Is `/data/local/tmp` readable by the debug APK itself (not just adb), on all three
   tiers?** The OS-level write/read has been confirmed on an API 35 device (2026-09-12) — a
   plain `adb push` followed by `adb shell ls` shows the file present and world-readable. What
   is still unconfirmed is whether the **sandboxed app process** can open that path once
   installed; adb shell runs as the `shell` user, which has broader filesystem access than an
   app UID. `lion` (API 34) has not been tried at all.
2. **Should the fixture corpus be committed?** It affects more than this subphase — the whole
   scenario suite depends on untracked files today.
3. **One image or several?** One is enough for a latency median. If metric 2 should later
   cover a rejected-photo path as well, that is a second image and a second decision.

## Plan rating: 8/10

**Pros.** It is small, it is honest about a conflict the parent phase did not see, and the
recommended option costs the production build nothing at all — no asset, no permission in
release, no APK growth. It can be proven end to end on a USB phone before a single Firebase
run is spent, which matters given the 5-runs-per-day Spark cap. It also refuses the tempting
shortcuts explicitly: no shrinking the image to save bytes, no synthetic image to dodge the
problem, and no silent skip if the file cannot be read.

**Cons.** The central technical question — whether the pushed file is actually readable on
API 34 and 35 — is not answered here, only scheduled, so the recommendation could still flip
to option B after hardware contact. It depends on a phone being available, which nothing in
this repository can guarantee. The git-tracking problem is flagged and deliberately not
solved, so it can still bite later. And the whole subphase exists to unblock one report-only
metric with no threshold attached, which is real but modest value for a document of this
length.
