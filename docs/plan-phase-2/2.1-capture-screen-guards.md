# Subphase 2.1 — guard the capture camera screen while a capture is in flight

Status: implemented, device-verified (2026-09-23) -- user confirmed "it works great now";
widget-test steps deferred, see below

Surfaced during the user's device check of phase 2 (2026-09-23), after phase 2's own waits
were confirmed working: "I could still click buttons like reference object and when I try to
quit it could quit for some reason." Phase 2 guarded the *review* screen's busy state; the
camera screen it sits on top of was never in phase 2's scope. This is a new finding, not a
regression from phase 2.

Two items flagged earlier in phase 2's check and deferred at the time are folded in here,
because they are the same class of defect on the same screen: work in flight that the UI does
not fence off.

## Goal

While a capture is being processed, the camera screen should fence off the controls that can
corrupt or double-run that work. Leaving stays allowed — but a capture the user leaves should
write nothing at all, rather than leaving a permanent, resultless row in Records.

## Design/Approach

### Finding 1 — five unguarded controls during `_saving`

Observed on device (the user could tap them); confirmed by reading `capture_screen.dart`.
Two of the screen's controls already consult `_saving`; five do not.

Guarded today: the shutter (`capture_screen.dart:634`) and the bottom-bar gallery button
(`:621`).

Not guarded:

| Control | Line | Handler |
|---|---|---|
| Reference chip ("Set reference" / current reference) | `:596` | `_openReferenceConfig` |
| "Change reference" icon, bottom bar | `:668` | `_openReferenceConfig` |
| "Close camera" X | `:489` | `context.pop()` |
| "Capture tips" help icon | `:505` | `_showGuidance` |
| "Choose from gallery", camera-unavailable fallback | `:560` | `_pickFromGallery` |

The last row is the sharpest of the five: it is the *same action* as the guarded button at
`:621`, reachable from a second place, with no guard. Two taps run two picks. The rest are
severity-ordered below it — they let the user open sheets over in-flight work, and in the
reference chip's case mutate `_reference` after the shutter has already fired.

Approach: route every control on this screen through the same `_saving` check the shutter
already uses, rather than adding a second mechanism. Decide per control whether "guarded"
means disabled or means allowed-but-deferred; see Open questions.

### Finding 2 — no `PopScope` on the capture screen

Phase 2 added a `PopScope` to `/analysis` only. `capture_screen.dart` has none, so system
back and back-gesture both leave mid-processing with no warning. The screen's own X button
(`:489`) is the third route out and is equally unguarded.

**Decided (2026-09-23, user):** leaving is allowed and not warned about. Phase 2 chose
warn-once for `/analysis` because the run completes and persists something useful in the
background; here, under finding 3's decision, leaving produces nothing, so there is nothing
to warn about and nothing to preserve.

Approach: no `PopScope` on this screen. The X button at `:489` keeps working as it does now.
What changes is not the exit but what the exit leaves behind, which is finding 3's job — the
two findings were only separable while the save question was open. Recorded as a deliberate
"no widget added" so a later reader does not read the absence as an oversight.

### Finding 3 — leaving mid-capture leaves a resultless Records row

**Not observed on device; derived from reading the code.** The user observed only that
quitting was possible. The consequence below is what the code says happens, and the device
check in Steps is what would confirm it.

In both `_capture` and `_pickFromGallery`, the database writes land *before* the
`mounted` check that abandons the rest of the method:

- `_capture`: `_ensureSession()` at `:258`, `markCaptured(...)` at `:259`, `if (!mounted)
  return;` at `:266`.
- `_pickFromGallery`: `_ensureSession()` at `:306`, `markCaptured(...)` at `:307`,
  `if (!mounted) return;` at `:314`.

`createDraftScan` (`app_database.dart:297`) inserts the scan with status `draft`;
`markCaptured` (`:317`) flips it to `captured` and stores the image path. Both complete
regardless of whether the screen still exists. The review step, which is what would carry
the scan forward, never runs.

`watchRecentScans` (`records_dao.dart:22-29`) filters on `deletedAt.isNull()` only — there
is no status filter — so that scan is a visible Records row forever: captured, has a photo,
has no results, and no path back into the flow.

This is pre-existing and independent of phases 1, 2, and 2.1's other findings. It fires on
every abandoned capture, including ones predating this round.

**Decided (2026-09-23, user):** a capture the user quits out of is not saved at all. In the
user's words, "when it quits mid-capture it shouldn't be saved." That rules out the
mark-`cancelled` and soft-delete options, which both keep a row and then hide it; the scan
should never be written in the first place.

Approach: move `_ensureSession()` and `markCaptured(...)` to *after* the `mounted` check in
both `_capture` and `_pickFromGallery`, so the row is created only once the user actually
reaches the review screen.

Both calls must move together. Deferring `markCaptured` alone would leave the row created by
`_ensureSession` behind at status `draft`, and since `watchRecentScans` has no status filter,
a `draft` row is just as visible in Records as a `captured` one — the bug would change shape
rather than go away.

Two consequences to handle rather than discover later:

- `_ensureSession()` is also called by `_usePhoto` (`:358`), which already runs after review
  is reached. Once the capture path stops calling it, `_usePhoto` becomes the first creator
  of the session. Confirm nothing between the shutter and review depends on `_sessionId`
  being non-null.
- `markCaptured` currently receives `result.localPath`, `_mode` and `result.orientation` from
  local variables in the capture method. Deferring the write means those values have to
  survive into the review step; `_capturedResult` already holds them, so the write can key
  off that rather than re-plumbing arguments.

`ScanStatuses.cancelled` (`scan_flow.dart:25`) is declared and written nowhere. Under this
decision it stays unused — noted here so a later reader does not assume it was overlooked.
Nothing in this finding is a schema change: no `schemaVersion` increment, no migration, no
Drift regeneration.

### Finding 4 — `imageIdentityOf` hashes on the UI isolate

Flagged during phase 2's check, deferred then. `RunAndPersistPipelineUseCase.imageIdentityOf`
(`run_and_persist_pipeline_use_case.dart:400-403`) runs `sha256.convert(bytes)` synchronously
over the whole image on the UI isolate, on the "Verify reference" path.

Same bug shape subphase 1.1 fixed for decode/bake/encode, and the same fix shape applies
(`compute()`; `Uint8List` in, `String` out, both plainly sendable). Smaller in absolute terms
than the model call it precedes — tens of milliseconds, not seconds — so this is a jank fix,
not a freeze fix, and it should not be described as the cause of anything the user saw.

### Finding 5 — `_usePhoto` re-entrancy before its own guard arms

Phase 2 disabled the "Verify reference" button on `_saving`, which closes the *long* window.
A shorter one remains: `_usePhoto` (`:350`) awaits `_ensureSession()` at `:358` and
`recordOrientationAttestation` at `:360` before `setState(() => _saving = true)` at `:383`.
Between entry and the guard arming there are two database round-trips during which the button
is still enabled. A fast double-tap can enter twice and, via `_ensureSession`, create two
draft scans.

Approach: arm the re-entrancy guard on method entry rather than relying on the widget's
disabled state, which is always at least one frame behind. `_capture` and `_pickFromGallery`
do not have this gap — when `_reference != null` their path from entry to
`setState(() => _saving = true)` is synchronous — so this is specific to `_usePhoto`.

## Steps

- [x] Guard the five controls in finding 1 against `_saving`, reusing the existing check.
      Note the X button at `:489` is deliberately excluded — leaving is allowed.
- [x] Move `_ensureSession()` and `markCaptured(...)` past the `mounted` check in both
      `_capture` and `_pickFromGallery`, together, so a quit mid-capture writes nothing. Also
      removed `didChangeDependencies`' own eager `_createSession()` call — discovered during
      implementation that opening the screen alone already created a `draft` row before any
      photo was taken, which the plan as originally written did not cover. Folded into this
      step and this finding, not spun out, since it is the same decision ("not saved") applied
      to a call site the initial read missed.
- [x] Confirm nothing between shutter and review reads `_sessionId` — only `_ensureSession()`
      (now lazy) and the widget's own `_sessionId` field read it; nothing else in the file
      assumes it is set before a photo succeeds.
- [x] Move `imageIdentityOf`'s hash off the UI isolate via `compute()`.
- [x] Give `_usePhoto` an entry-guard that closes the pre-`_saving` await window; removed the
      now-redundant second `setState(() => _saving = true)` further down the method.
- [ ] Widget test: every control on the camera screen is non-interactive while `_saving`.
      **Deferred** — `CaptureScreen` has no existing widget-test harness and needs live
      `camera`/`image_picker` platform-channel mocks that nothing in this repo currently
      provides; building that is its own piece of work, separate from this fix. Device check

- [ ] Test: a capture quit before review leaves no scan at all — neither `captured` nor
      `draft` — visible to `watchRecentScans`. **Deferred for the same reason** — the
      assertion only has meaning exercised through `CaptureScreen`'s own methods, not through
      the DAO in isolation, since the fix is "don't call `_ensureSession`," not a query filter.
- [x] `dart format`, `flutter analyze`, targeted `flutter test`, then full `flutter test`.
      Results below.
- [x] Device check: tap each guarded control during processing and confirm nothing happens;
      quit mid-capture and confirm no new row appears in Records. **User confirmed, 2026-09-23:
      "it works great now."** No further detail on which specific controls or the pre-existing
      Records rows (open question 1) was given, so treat this as a pass on the reported
      symptoms (unguarded taps, quit) rather than a line-by-line confirmation of every control
      in the finding-1 table.

## Resolved questions

1. ~~**Back-press and X during capture: block, warn, or allow?**~~ Resolved 2026-09-23:
   allow, no warning. See finding 2.
2. ~~**What happens to the scan when the user leaves?**~~ Resolved 2026-09-23: it is never
   written. See finding 3. Questions 1 and 2 turned out to be one question — once leaving
   means nothing is saved, the second has only one answer left. They were separable only
   while the first was undecided.

## Open questions

1. **Rows already in existing databases.** The decision above stops *new* leftover rows; it
   does nothing about scans already written by the current build, which stay visible in
   Records as photos with no results. Options: leave them, offer a manual delete in Records,
   or clean them up once on launch. Not urgent and not blocking — the fix is correct without
   it — but it should be decided rather than forgotten, because every existing install has
   some.
2. **Does backgrounding the app count as leaving?** `mounted` stays true when the app is
   backgrounded, so under this fix a backgrounded capture still completes and still saves,
   which is almost certainly what the user wants. Flagged only so that nobody later "fixes"
   this by keying on lifecycle instead of `mounted` and silently starts discarding captures
   the user meant to come back to.
3. **Should the reference chip be disabled or merely deferred?** Disabling is simpler;
   however, a user who realises mid-processing that they picked the wrong reference has no
   way to say so, and will find out only at the review screen.

## Relationship to the rest of the round

Does not change phase 2's status — phase 2's scope (the two waits' progress UI) is device-
verified as of 2026-09-23. This subphase is about what the *rest* of the capture screen does
while that work is in flight. Phase 3's validation and documentation steps should run after
this subphase lands, so its widget tests and the `app-flow.md` edit describe the final
behaviour rather than being rewritten twice.

## Plan rating: 8/10

*(Was 7/10 before the 2026-09-23 decisions; the two blocking questions are now settled.)*

**Pros.** The findings are concrete, each anchored to a line that was read rather than
assumed, and severity is honestly ordered — finding 3 is the only one with a durable
consequence and it is stated as derived rather than observed. Findings 4 and 5 are folded in
on a real criterion (same screen, same class of defect) instead of being bundled for
convenience. Nothing blocking is left open, and the resolved decision is simpler than any of
the alternatives it displaced: deferring two writes removes the bug outright rather than
writing a row and then hiding it, so there is no status to maintain, no migration, and no
Records query change. The failure mode of a half-application (deferring one write but not the
other) is called out and has a test written against it. The key test is host-testable, which
keeps the device check to confirmation rather than discovery.

**Cons.** Finding 3 is genuinely a different bug from findings 1, 2, 4 and 5: it is a
data-lifecycle defect, pre-existing and independent of this round, and a stricter reading of
the scope rule would give it its own fix document rather than a seat here. Finding 4's
inclusion is the weakest — it is on the review path, not the camera screen, and rides along
on "same class of defect" more than on locality. Deferring the session creation also moves
`_usePhoto` into being the first writer of a scan, which is a small ordering change to a flow
that several other documents describe; phase 3's `app-flow.md` edit will need to reflect it.
The rating would be higher if finding 3 were split out into its own fix document.
