# Subphase 1.1 — the capture/gallery-pick freeze is a different bug than phase 1 fixed

Status: done, device-verified

Surfaced during the user's device check of phase 1 (2026-09-22): "the spinner works when
clicking 'confirm and analyze' … but the camera freezes before it goes to the page where you
have to verify it." Phase 1 only offloaded the two ML-inference FFI calls
(`classifyView`, `runPipeline`); it never touched this path, so this is a new finding, not a
regression from phase 1's change.

## Root cause

`_capture()` and `_pickFromGallery()` in `capture_screen.dart` both call
`ImageService.processCapture()`, which calls `processRawBytes()`
(`lib/core/utils/image_service.dart:20-55`):

```dart
final decoded = img.decodeImage(rawBytes);
final oriented = img.bakeOrientation(decoded);
final encodedBytes = Uint8List.fromList(img.encodeJpg(oriented, quality: 92));
```

All three calls are synchronous, pure-Dart, CPU-bound work from the `image` package (JPEG
decode, an EXIF-orientation bake that reallocates and rewrites the whole bitmap, then a
quality-92 JPEG re-encode), with no `await` between them. `processRawBytes` is `async` in
signature only — exactly the same shape of bug phase 1 fixed for the ML calls, but this one
has nothing to do with `dart:ffi`, ONNX Runtime, or the native library. It runs entirely on
the UI isolate and blocks it for the whole decode-bake-encode chain, which is why the
shutter's own spinner (`capture_screen.dart:649`) freezes instead of animating: no frame is
pumped while it runs, same mechanism, different source.

Images from `image_picker`/`CameraController` can be up to 3000×3000 (the `maxWidth`/
`maxHeight` passed to `pickImage`), so this is not a trivial amount of work on a low-tier
device.

## Design/Approach

Same fix shape as phase 1, applied to a Dart-only workload instead of an FFI one:

- Move `img.decodeImage` / `img.bakeOrientation` / `img.encodeJpg` off the UI isolate.
  `compute()` (Flutter's `Isolate.run`-based helper) is the natural fit here, more so than
  phase 1's raw `Isolate.run` + native-context plumbing, because the entire input (`rawBytes`)
  and output (`CapturedImageResult`'s fields) are plain, fully sendable Dart values — no
  native pointer, no shared native context to reopen.
- `CapturedImageResult` itself must stay a sendable/reconstructible shape across the isolate
  boundary (check its fields — likely already plain `Uint8List`/`int`/`String`/enum, but
  verify before assuming).
- File I/O (`getTemporaryDirectory()`, `File.writeAsBytes`) should stay on the calling isolate
  after the compute call returns the encoded bytes — `path_provider` and `dart:io` file
  handles are not guaranteed to behave identically off the main isolate on every platform, and
  the existing code already treats the write as a separate, best-effort step (falls back to
  `originalPath` on failure). No need to move it.
- `_capture()`/`_pickFromGallery()` already show a busy indicator (`_saving`) during this
  call — this subphase does not need new UI, only for the existing indicator to actually
  animate, which is the same "prove it's not just painted once" verification phase 1 used.

## Steps

- [x] Confirmed `CapturedImageResult`'s fields are plain (`Uint8List`, `int`, `String?`, the
      `CaptureOrientation` enum) — no change needed there; `width`/`height` were already
      derived at the call site from `oriented.width`/`oriented.height`, not from the class
      itself.
- [x] Extracted the decode/bake/encode chain into a top-level `_decodeBakeEncode(Uint8List)`
      in `image_service.dart`, returning `(Uint8List, int, int)` (encoded bytes, width,
      height) — a record, not a custom class, since only records/primitives/collections of
      those are guaranteed sendable back across the isolate boundary. Run via `compute()`.
- [x] `processRawBytes` now `await compute(_decodeBakeEncode, rawBytes)`, then does the
      existing file-write and `CapturedImageResult` construction unchanged, using the
      returned `width`/`height` in place of `oriented.width`/`oriented.height`.
- [x] `dart format` / `flutter analyze` clean; `test/core/utils/image_service_test.dart`
      needed no changes — it already awaited every `processRawBytes` call.

## Verification

Commands run:

```
dart format lib/core/utils/image_service.dart
flutter analyze lib/core/utils/image_service.dart
flutter test test/core/utils/image_service_test.dart

```

Results:

- `dart format`: reformatted once (line wrap from the record-returning signature); no
  further changes.
- `flutter analyze`: no issues found on the changed file.
- `flutter test test/core/utils/image_service_test.dart`: 10/10 passed, including "throws
  Exception on corrupt image bytes" — confirms an exception thrown inside `compute()`
  correctly propagates to the awaiting `Future`, not swallowed by the isolate boundary.
- `flutter test` (full suite): 122 passed, 39 skipped — unchanged from phase 1's count (this
  subphase changed an implementation, not test coverage, and the existing suite already
  exercised the changed function).

**Device-verified (2026-09-23):** sideloaded, confirmed working — the shutter/gallery-pick
spinner animates through to the review screen with no frozen interval. User's own words:
"works great now."

## Relationship to phase 1 and phase 2

This does not change phase 1's status — phase 1's own scope (the two ML-inference waits) is
still host-verified with its own device check still owed, tracked separately in
`1-isolate-offload.md`. This subphase is a third, independent freeze point, found only
because the user was doing that device check. Phase 2 (progress UI) should not be built for
`/analysis` or the review screen's "Verify reference" step until this subphase's fix is in,
or the capture screen's existing `_saving` spinner will keep freezing regardless of anything
phase 2 adds downstream.
