# Phase 3.1 — Host-side re-mark replay of the recorded 18 marks

Status: done 2026-09-10

Opened 2026-09-10, after phase 3 closed and before phase 4 starts. This subphase exists
because phase 4's verdict is currently blocked on an APK sideload, and the data needed to
answer most of its question already exists on disk.

## Symptom

Phase 3 measured the composed transform on the PIGRGB stock corpus with a synthetic ±1%
`cm_per_px_actual` sweep: worst-case spread 14.7% → 10.9% at 1280 px, 11.9% → 10.3% native.
The band this round exists to shrink was never measured there. It was measured on device, on
three field photos, by re-marking a real reference stick: **5.18% / 12.04% / 12.55%**
(`docs/fix-phase-2/2.1-reference-length-sensitivity.md`, raw data in
`docs/logs/recorded.md` round 2).

Those are two different instruments on two different corpora, so phase 3's improvement cannot
be compared to the number the round is judged against. `docs/fix-3.md`'s own plan rating names
this as the round's second-largest weakness.

## Root cause of the gap

`ML/host_scale_test/jitter_sweep.py` sweeps `cm_per_px_actual` by percentage deltas because
the PIGRGB images carry no reference object to mark — a *proxy* for marking noise — and they
are 960×540, where the double-raster detour this round removed is ~1.5×, versus 4.7× on a
2250×3000 gallery import. The three `.pig_pictures/` photos have neither problem, and
`docs/logs/recorded.md` round 2 records the exact `ref_px` the user marked on each of 18
device scans; `cm_per_px_actual = reference_cm / ref_px` reconstructs each mark exactly.

## Change made

`ML/host_scale_test/remark_replay.py` — replays those 18 marks through the corrected pipeline
without a phone:

1. **Prepare each photo.** Sources are 3024×4032, EXIF orientation 1 (asserted — AGENTS rule
   5). Recorded scans came through `pickFromGallery` (long edge capped at 3000), so each is
   resized to **2250×3000**, lossless PNG. HEIC via `pillow_heif` — OpenCV 5.0.0 here returns
   `None` for HEIC.
2. **Reconstruct each mark** as above (`reference_cm` = 100 for the meter stick, 131 for both
   porac sticks).
3. **Run the shipped host CLI**, cwd = build dir so the local `onnxruntime.dll` wins over the
   System32 copy (README's trap).
4. **Compare** per-mark `predicted_kg` / `mask_area_px` / `seg_conf` / `ladder_rung` /
   `kept_fraction` and per-photo spread `(max − min) / min` against the recorded device bands.

Output: `ML/host_scale_test/out/remark_replay.json`.

## Validity gate — read this before any weight number

`docs/logs/recorded.md` round 2 also recorded `segArea` (`construction.mask_area_px`) and
`seg conf` per mark — the device's own segmentation, upstream of everything this round
changed. **The replay is only evidence if the host reproduces them:** `ladder_rung` 0 on
every mark, `seg_conf` near 0.915–0.922, and `mask_area_px` tracking the recorded `segArea`
*including its step pattern* (which marks share an identical area — a host run that varies
smoothly is measuring a different mask).

Known divergences, none fixable here: the image reaches the host through libheif +
OpenCV-resize rather than Android's picker and decoder, so the YOLO input is not
bit-identical; `weight_branch_cli` runs no quality gates (both manifest flags ship `false`)
and always predicts. If the gate fails, this subphase reports that, not a spread on a mask
the device never saw.

## Outcome

Ran 2026-09-10. `ML/host_scale_test/remark_replay.py`, raw data in `out/remark_replay.json`.

### Validity gate — passes on all three photos

| photo | `ladder_rung` | host `seg_conf` vs device | host `segArea` vs device (worst mark) | step pattern |
|---|---|---|---|---|
| 92 kg | 0 on all 6 (device: 0) | 0.919–0.922 vs 0.919–0.922 | −0.130% (mark 6); marks 1–5 byte-identical | reproduced: constant marks 1–3, jump at 4, jump at 6 |
| 96 kg | 0 on all 6 | 0.915–0.917 vs 0.915–0.917 | +0.062% (mark 2) | reproduced: mark 1 high, dip at 2, constant 3–6 |
| 118 kg | 0 on all 6 | 0.918–0.920 vs 0.918–0.920 | +0.077% (mark 1) | reproduced: mark 1 high, constant 2–3, constant 4–6 |

The host is segmenting the same masks the device did — same rung, same confidence to the
fourth decimal, same area to within 0.13%, and the same *pattern* of which marks share an
identical area. The libheif + OpenCV-resize decode path is close enough to the device's that
the segmentation stage is not a confound. Weight numbers below are therefore comparable.

### Bands: device (old two-step raster) vs host (composed transform)

| photo | device band | device spread | host band | host spread |
|---|---|---|---|---|
| 92 kg | 83.54–88.03 | **5.18%** | 83.02–88.02 | **6.03%** |
| 96 kg | 78.53–88.84 | **12.04%** | 87.36–89.37 | **2.29%** |
| 118 kg | 104.80–118.49 | **12.55%** | 106.69–114.20 | **7.04%** |

### Reading

**Mixed-to-positive, and it does not close phase 4.**

- **118 kg — a real improvement, 12.55% → 7.04%.** `kept_fraction` is 0.93–0.94 across all
  six host marks with no dropout on either side, `segArea` tracks the device tightly, yet the
  band roughly halved. This is the cleanest evidence the composed transform reduces the
  boundary-feature jitter (F53 item 4) — though 7% is still large.
- **96 kg — improvement, partly confounded.** The device's 12.04% was driven by a single
  cutter dropout at mark 3 (`kept_fraction` 0.8063, 78.53 kg), which `docs/logs/recorded.md`
  already flags as the recurring V176 failure, not raster jitter. The host did not hit that
  dropout (`kept` 0.9527 at the same mark), so the tighter host band cannot be fully credited
  to the transform.
- **92 kg — no improvement (5.18% → 6.03%).** `segArea` is byte-identical across host marks
  1–3, yet `kept_fraction` splits 0.869 / 0.869 / 0.953 and the weight jumps 83.0 → 83.2 →
  88.0 with it. The cutter still makes a discrete choice on an identical mask — F53 item 3,
  "cutter on the resampled grid", which ADR-005 names the dominant error term. The composed
  transform moved *which* marks land on which side of that jump; it did not remove the jump.

**Verdict.** The round does what its scope claims — it removes the double rasterization, and
on the one photo where the cutter is stable across all marks (118 kg) that shows up as a
halved band. It does not fix the cutter's discreteness, which is a separate term and out of
this round's scope. The polygon hypothesis is neither promoted nor retired by this: the 92 kg
null is explained by the cutter, not by the transform being wrong.

### Not done here

A host *before* number — `weight_branch_cli` rebuilt against `scale_mask_to_training_space`
— would remove the device-decoder confound entirely and isolate the transform's effect on
the same machine. That is a rebuild, deferred. Phase 4's on-device re-mark remains the real
verdict; this subphase says to expect a mixed result there, with the 118 kg photo improving
most and the 92 kg photo roughly flat.

## Plan rating: 8/10

**Pros.** Reuses recorded data instead of asking for new collection; closes the gap the
round's rating calls out (measuring on the field corpus, not stock images); the validity gate
is built from numbers the device published, so the replay can be falsified; cheap — one
script, no rebuild, no sideload, same binary phase 3 was measured with. The gate passing is
itself a result: the host segmentation is faithful.

**Cons.** It cannot reproduce the device decode path, so the device-vs-host comparison still
carries a decoder confound on the cutter/feature stage (the gate only clears it for
segmentation) — a host *before* rebuild would remove it. Two photos need a HEIC decode the
device never did. The CLI duplicates `pipeline.cpp` by hand with nothing enforcing sync
(open since round 9). A clean band here would still leave the live-camera path, the disabled
quality gates, and the ~73 kg floor untouched.
